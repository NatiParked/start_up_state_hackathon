## Error Handling

**Pattern: try/finally with error captured into reactive state**

Frontend stores and composables use the same shape: `isLoading` ref + `error` ref + `try { ... } catch { error.value = e } finally { isLoading.value = false }`.

Example (`goed/src/stores/startups.js:55`):
```js
async function fetchAll() {
  isLoading.value = true
  error.value = null
  try {
    const { data, error: dbError } = await supabase.from('map_startups').select('*')
    if (dbError) { error.value = dbError; return }
    companies.value = data ?? []
  } catch (e) {
    error.value = e
  } finally {
    isLoading.value = false
  }
}
```

**Supabase calls:**
- Always destructure with renamed `error` to avoid shadowing the outer `error` ref: `const { data, error: dbError } = await supabase...`
- Treat returned `error` as a value, not a thrown exception
- Use `.maybeSingle()` (not `.single()`) when the row may not exist (see `router/guards.js:24`, `composables/useAdminAuth.js:39`)

**Edge Functions:**
- All operational errors return a structured JSON body via the `errorResponse(code, message, status)` helper (`supabase/functions/onboard-company/index.js:52`)
- Standard error codes: `'INVALID_INPUT'` (400/405), `'INTERNAL_ERROR'` (500)
- Outer `try/catch` wraps the entire request handler (`onboard-company/index.js:121`)
- Non-fatal errors (e.g., audit-row insert failures) are logged but do not change the response status — see `onboard-company/index.js:223`
- Always include CORS headers on every response (preflight, success, and error)
- Required env vars throw a descriptive `Error` on access (`supabase/functions/_shared/supabaseAdmin.js:24`)

**Form validation:**
- URL validation uses `new URL(value)` inside a `try/catch` — see `goed/src/components/submit/SubmitForm.vue:16` and `supabase/functions/onboard-company/index.js:111`

## Function and Module Design

**Composables (`goed/src/composables/`):**
- One responsibility per composable; return a plain object of refs/computed/functions
- Module-level state is acceptable for true singletons — see `useAdminAuth.js:7` (single auth-state subscription guarded by `subscribed` flag)
- Always return refs rather than raw values so consumers stay reactive

**Pinia stores:**
- Composition-API style only: `defineStore('id', () => { ... return { ... } })` — no `state/getters/actions` object form
- Always include `isLoading` and `error` refs in any store that fetches data ("convention-required" — see comment in `stores/filters.js:21`)
- Use `storeToRefs(store)` in consumers to keep state reactive while destructuring (action functions can be destructured directly because they aren't reactive)

**Vue components:**
- Props are typed via the verbose object form: `defineProps({ company: { type: Object, required: true } })`
- Emits declared via `defineEmits(['submit'])`
- Computed properties wrap derived values *and* class strings (heavy use to keep templates declarative)
- Animations: GSAP for transitions/orchestration (`CompanyDrawer.vue:52`, `SubmitProgress.vue:39`); raw CSS `@keyframes` only for tiny one-shot fades (`MapView.vue:47`)

**Edge Functions:**
- File-level JSDoc block at the top describing purpose + `curl` usage example (see `onboard-company/index.js:1`)
- Define small helpers (`jsonResponse`, `errorResponse`, `scalarColumns`) inline before the `Deno.serve(...)` handler
- Always handle CORS preflight (`OPTIONS`) as the first check
- Validate method, then parse body, then validate fields, then run business logic — all guarded with early-return error responses

**Constants:**
