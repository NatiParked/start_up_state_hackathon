```js
// Manages the Navigator resource corpus fetched from Supabase.
// Used by: NavigatorView, ResourceCard, NextStepsGuide
// goed/src/stores/resources.js
import { defineStore } from 'pinia'
import { ref, computed } from 'vue'

export const useResourcesStore = defineStore('resources', () => {
  // state
  const items = ref([])
  const isLoading = ref(false)
  const error = ref(null)

  // getters
  const count = computed(() => items.value.length)

  // actions
  async function fetchAll() {
    isLoading.value = true
    try {
      // supabase call
    } catch (e) {
      error.value = e
    } finally {
      isLoading.value = false
    }
  }

  return { items, isLoading, error, count, fetchAll }
})
```

**Conventions:**

- Store id (string passed to `defineStore`) matches the file name (`resources.js` → `'resources'`)
- Export named `useXxxStore`
- Always return all state/getters/actions you want public from the setup function
- Use `storeToRefs(store)` in components when destructuring state to preserve reactivity:
  ```js
  import { storeToRefs } from 'pinia'
  const store = useResourcesStore()
  const { items, isLoading } = storeToRefs(store)
  const { fetchAll } = store  // actions can be destructured directly
  ```

## Component Design Patterns

**File structure** (where new code goes):
- `goed/src/components/` — reusable UI components (buttons, cards, drawers, form fields)
- `goed/src/views/` — route-level page components (one per route)
- `goed/src/composables/` — reusable composition functions (e.g., `useGsapEnter.js`, `useGeocode.js`)
- `goed/src/stores/` — Pinia stores
- `goed/src/router/` — Vue Router config (already exists at `goed/src/router/index.js`)
- `goed/src/lib/` — non-Vue utilities (e.g., Supabase client, API wrappers). Always `lib/`, never `services/`.
- `goed/src/assets/` — static assets and global CSS

**SFC block order — always `<script>` first, then `<template>`, then `<style>`:**

```vue
<script setup>
// 1. imports
// 2. defineProps() / defineEmits()
// 3. composable calls  (useXxx(), storeToRefs, etc.)
// 4. ref() state declarations
// 5. computed() declarations
// 6. methods (plain functions)
// 7. watch() / watchEffect()
// 8. lifecycle hooks (onMounted, onUnmounted, etc.)
</script>

<template>
  <!-- markup — no logic here (see rules below) -->
</template>

<style scoped>
/* component-local styles — use sparingly; prefer Tailwind utilities */
</style>
```

**No logic in templates — ever:**

Templates are pure rendering surfaces. All derived values, conditional classes, visibility decisions, and display formatting belong in `computed()`, not in the template.

```vue
<!-- WRONG — ternary, boolean logic, and function calls in template -->
<template>
  <div :class="isHiring ? 'text-green-600' : 'text-gray-400'">
    {{ company.job_titles.length > 3 ? company.job_titles.slice(0, 3) : company.job_titles }}
  </div>
  <span v-if="sector && stage">{{ sector.toUpperCase() }}</span>
</template>

<!-- RIGHT — all decisions in computed, template just reads -->
<script setup>
const hiringClass = computed(() =>
  props.company.is_hiring ? 'text-hiring-green' : 'text-gray-400'
)
const visibleJobTitles = computed(() => props.company.job_titles.slice(0, 3))
const hasMeta = computed(() => Boolean(props.company.sector && props.company.stage))
const sectorLabel = computed(() => props.company.sector?.toUpperCase() ?? '')
</script>

<template>
  <div :class="hiringClass">
    <span v-for="title in visibleJobTitles" :key="title">{{ title }}</span>
  </div>
  <span v-if="hasMeta">{{ sectorLabel }}</span>
</template>
```

**Rules enforced strictly:**
- No ternary operators (` ? : `) in template expressions
- No boolean operators (`&&`, `||`, `!`) in `:bind` or `v-if` expressions
- No arithmetic in templates
- No method calls for derived values (use `computed` instead)
- No inline object/array literals in `:bind` (e.g., `:style="{ color: x ? 'a' : 'b' }"`) — compute the object
- Event handlers (`@click`, `@submit`) are the only functions permitted in templates

**`computed()` as the template foundation:**

Every piece of display logic — CSS classes, visibility flags, formatted strings, filtered/sliced arrays, conditional labels — is a `computed`. The template reads named values; it never decides anything.

When multiple display properties share the same dependencies, group them into a single computed object to co-locate the logic:

```js
// Good — related display properties share the company prop dependency
const companyDisplay = computed(() => ({
  name: props.company.name,
  logoUrl: props.company.logo_url ?? monogramUrl(props.company.name),
  sectorLabel: props.company.sector?.toUpperCase() ?? '—',
  regionLabel: props.company.region ?? 'Utah',
}))

// Good — separate when dependencies differ meaningfully
const hiringBadge = computed(() => ({
  visible: props.company.is_hiring && props.company.job_titles.length > 0,
  count: props.company.job_titles.length,
  hasMore: props.company.job_titles.length > 3,
  overflowCount: props.company.job_titles.length - 3,
}))
```

Note: a `computed` object re-evaluates its entire getter when **any** of its tracked dependencies change — there is no per-key invalidation. This is generally fine (the cost is a few property reads). Split into separate `computed`s when keys have significantly different dependency trees or expensive derivations.

**Ref discipline:**
- Use individual `ref()` for each distinct piece of state — no `reactive()` grouping needed
- If a component accumulates 15–20+ `ref()` declarations, treat it as a design signal: the component may be doing too much and should be split into smaller components or composables

**Props and emits:**
- Define with `defineProps({ name: { type: String, required: true } })` — object form only (not array form), so types and defaults are always explicit
- Define with `defineEmits(['update', 'close'])` — list events explicitly
- Validate prop types and provide `default` values where reasonable

**Composition over inheritance:**
- Pull reusable logic into composables in `goed/src/composables/`, not mixins
- Component size is a soft guideline (~200 lines), but complexity (too many refs, too many concerns) is the real split signal

**Accessibility & semantics:**
- Use semantic HTML (`<button>`, `<nav>`, `<main>`, `<section>`)
- Always include `rel="noopener noreferrer"` on `target="_blank"` links

**Animation pattern:**
- Simple, one-off GSAP animations (`gsap.to(el, { ... })`) can be inline in `onMounted` or an event handler
- Extract to a composable only when the animation logic is complex or reused across multiple components

## Error Handling

No patterns are established yet. **Conventions to apply:**

**In Pinia stores (async actions):**

## Function Design

- **Size:** Prefer small, focused functions. If a function exceeds ~30 lines, look for an extraction.
- **Parameters:** When a function takes more than 2-3 args, switch to a single options object (`{ filters, sort, limit }`) so call sites are self-documenting.
- **Return values:** Be consistent — always return the same shape from a function. **Service-layer functions in `goed/src/lib/` must return `{ data, error }` to mirror Supabase conventions.** Never return `null` sometimes and an object other times.
- **Async:** Use `async/await`, not raw `.then()` chains.
